# 开源项目官网应具备的结构与文档库拆解

> 本文面向希望搭建或重构开源项目官网的团队，回答两个问题：
> 1. 一个开源项目官网**应该有哪些核心结构**？
> 2. 以 **AgentScope Java** 为例，一个真实的官网文档库**是怎么组织的**？

---

## 1. 一个开源项目官网应有的核心结构

开源项目官网的本质是「**项目的名片 + 用户手册 + 开发者入口**」。一个成熟的开源官网通常由以下核心结构组成。

### 1.1 官网整体应包含的页面模块

| 模块 | 作用 | 是否必需 |
| --- | --- | --- |
| **首页 / Landing** | 一句话说清项目是什么、解决什么问题，放 Logo、Slogan、Star、快速上手入口 | 必需 |
| **快速开始（Quick Start）** | 让用户 5 分钟跑通最小示例，决定留存率 | 必需 |
| **核心概念 / 指南** | 讲解设计思想、核心抽象、关键概念 | 必需 |
| **使用手册（Guide/Tutorial）** | 按场景组织的手把手教程 | 必需 |
| **API / 参考手册（Reference）** | 类、方法、配置项、CLI 的完整参考 | 必需 |
| **集成 / 生态（Integration）** | 与第三方（模型、存储、框架、渠道）对接 | 推荐 |
| **博客（Blog）** | 版本发布、技术深潜、最佳实践 | 推荐 |
| **社区（Community）** | 贡献者指南、加入社区、联系方式 | 推荐 |
| **常见问题（FAQ）** | 高频问题速查 | 推荐 |
| **变更日志（Change Log）** | 版本变更说明 | 推荐 |

### 1.2 文档库应有的目录结构

一个好的文档库目录结构应做到「**按语言隔离、按版本隔离、按内容类型分区**」：

```
docs/
├── docs.json              # 站点配置：导航/版本/语言/品牌/重定向（单一事实来源）
├── package.json           # 依赖与脚本（本地预览、校验、测试）
├── assets / imgs/         # 共享图片与静态资源（按功能/模块分区）
├── examples/              # 示例代码/场景素材，供教程引用
├── scripts/               # 校验脚本、自动化工具
├── v2/                    # 当前版本
│   ├── en/                #   英文
│   │   ├── intro.md       #     首页
│   │   ├── docs/          #     SDK/使用指南
│   │   ├── service/       #     服务端产品文档
│   │   ├── integration/   #     集成
│   │   ├── blogs/         #     博客
│   │   └── community/     #     社区
│   └── zh/                #   中文（与 en 平行对齐）
└── v1/                    # 历史版本（结构同 v2）
```

### 1.3 核心技术基础设施

| 能力 | 说明 |
| --- | --- |
| **文档生成框架** | Mintlify / Docusaurus / VitePress 等，支持纯 Markdown 写作 + 自动生成站点 |
| **版本控制** | 文档纳入 Git 仓库，锁定依赖版本，保证本地与 CI 一致 |
| **多语言** | 默认语言 + 翻译语言，目录按语言隔离，路径对齐 |
| **多版本** | 历史版本与当前版本并存，可切换 |
| **检索功能** | 站内搜索（如 Mintlify 搜索） |
| **自定义能力** | 允许自定义 JS / CSS（如首页交互、品牌化样式） |

### 1.4 站内搜索能力要求

站内搜索是官网文档的刚需。以 Mintlify 为例，搜索为**内置能力**（全文搜索 + `Cmd+K` 快捷键），但启用有明确要求：

**① 本地预览（`mint dev`）需先登录**

```bash
mint login    # 浏览器授权 Mintlify 账号，登录一次即可
```

- 官方要求：必须认证 CLI 账号后才能启用搜索与 AI assistant。
- 凭据保存在 `~/.config/mintlify/config.json`，跨会话保持登录；验证状态用 `mint status`。
- 未登录时页面仍可预览，但搜索框与 assistant 不可用。

**② 线上托管默认开启**

发布到平台托管后搜索自动可用，构建时自动生成索引，无需额外配置。

**③ 注意索引排除规则**

以下情况会使页面从搜索索引排除：`hidden: true`（版本/Tab/分组）、页面 front-matter 的 `hidden`/`noindex`/`searchable: false`、未列入导航的页面。需保留搜索时用 `searchable: true` 或 `seo.indexing: "all"`。

### 1.5 配置驱动的导航设计

官网导航应**配置化**，而不是在代码里写死。典型五层结构：

```
语言（en/zh） → 版本（v2/v1） → Tab（顶部栏目） → 分组（侧边栏） → 页面（md 文件）
```

好处：增删栏目、调整顺序、多语言多版本全部通过一份配置文件维护，文档作者无需懂前端。

### 1.6 质量保障闭环

```
写作 → 本地预览（npm run dev）→ 自动化校验（链接/锚点/title/导航）→ CI 校验 → 自动发布
```

- **自动化校验**：脚本检查链接、锚点、资源、导航可达性、缺失 title。
- **CI 自动化**：PR / push 时自动运行校验，防止坏链与错配。
- **自动发布**：接入平台（Mintlify App / GitHub Pages / 静态托管），提交即发布。
- 每条约束都要有「校验兜底」，例如：每个页面必须有 `title`、导航里出现的路径必须有对应文件、本地图片/链接必须存在、旧链接必须重定向。

### 1.7 首页 Landing 的核心元素

首页是用户对项目的第一印象，通常由以下元素组成：

| 元素 | 说明 |
| --- | --- |
| **Hero 区** | 一句 Slogan + 副标题，说清「解决什么问题」；配项目 Logo 与 GitHub Star |
| **CTA 按钮** | 「快速开始 / Quick Start」「查看文档 / Docs」「GitHub」等主次入口 |
| **安装命令区** | 直接给出 `pip install` / `mvn` / `npm install` 一行命令，用户复制即用 |
| **产品亮点（Features）** | 3~6 个核心能力卡片，配图或代码示例 |
| **代码示例窗口** | 多语言/多场景 Tab 切换展示「Hello World」或核心用法，降低上手门槛 |
| **采用者/信任墙** | 企业 Logo 墙、行业标签跑马灯、用户评价，增强可信度（如「Battle-tested in Production」） |
| **功能分栏（Sections）** | 按主题深入介绍：架构、Harness、集成、性能等，每段配「了解更多 →」链接 |
| **特性卡片网格（Cards）** | 用卡片网格罗列关键能力（模型容错、上下文工程、中间件、工具/MCP、多智能体等） |
| **FAQ 折叠区** | 用折叠组件（Accordion/details）直接列出 4~6 个高频问题，减少跳转 |

### 1.8 导航栏、侧边栏与页脚

| 结构 | 内容 | 设计要点 |
| --- | --- | --- |
| **顶栏（Navbar）** | Logo + 文档名、主要栏目（Tabs）、语言切换、版本切换、GitHub / 外部链接 | 首页与文档页共用，保持品牌一致 |
| **侧边栏（Sidebar）** | 当前栏目下的分组与页面树，可多级嵌套 | 分组命名清晰，层级不超过 3 级为宜 |
| **页脚（Footer）** | 版权、许可证、项目地址、社交图标、站点地图 | 至少包含仓库链接与许可证 |

语言/版本切换是开源官网的刚需（国际化 + 多版本并存），应放在顶栏且全局可见。

### 1.9 品牌化、SEO 与元信息

| 能力 | 说明 |
| --- | --- |
| **品牌色** | 主色/亮色/暗色统一配置（如 Mintlify `colors` 的 primary/light/dark） |
| **Logo 与 Favicon** | 明/暗两套 Logo 适配主题；favicon 统一品牌图标 |
| **页面元信息** | 每页 `title` + `description`，用于浏览器标签、SEO、站内检索 |
| **社交分享** | Open Graph（og:title/description/image）与 Twitter Card，链接分享时显示卡片 |
| **站点地图** | sitemap.xml 供搜索引擎抓取 |
| **结构化数据** | 如需要可加 JSON-LD（软件应用、文档）提升搜索表现 |

### 1.10 开发者体验与社区配套

一个「好用」的开源官网还应具备以下配套：

| 结构 | 说明 |
| --- | --- |
| **404 页面** | 自定义 404，提供返回首页与搜索入口，避免死胡同 |
| **贡献指南** | CONTRIBUTING.md / 社区页，说明如何提 Issue、PR、参与开发 |
| **贡献者展示页** | 展示活跃贡献者（头像 + GitHub ID + 简介表格），数据来自 GitHub，鼓励参与 |
| **许可证与法律信息** | 明确开源许可证（Apache-2.0 / MIT 等）、版权声明 |
| **发布说明** | Release Notes / Change Log，每次发布同步更新 |
| **路线图（Roadmap）** | 公开未来规划，吸引社区参与 |
| **使用场景 / 案例（Use Cases）** | 真实客户或典型场景案例，增强说服力 |
| **示例素材库（examples/）** | 随文档提供示例代码、数据文件，供教程场景引用下载 |
| **支持渠道** | GitHub Discussions / Issues / 邮件 / 社群二维码 |
| **分析埋点** | 站内流量统计（可选，帮助了解用户行为） |

### 1.11 核心结构清单（Checklist）

```text
[ ] 内容体系：首页 / 快速开始 / 概念与指南 / 使用手册 / API 参考 / FAQ / 变更日志
[ ] 生态与案例：集成集成 / 博客 / 使用场景
[ ] 社区：贡献指南 / 贡献者展示 / 支持渠道
[ ] 导航：多语言切换 + 多版本切换 + 配置化导航
[ ] 品牌与 SEO：Logo / 颜色 / favicon / 元信息 / sitemap
[ ] 体验：检索 / 自定义 404
[ ] 质量与发布：校验 + CI + 自动发布 / 许可证
```

### 1.12 文档的由浅入深结构设计

一个开源项目官网的文档库，除了「有哪些模块」，更要讲究**信息的递进关系**——让读者从陌生到上手、从入门到深入，始终有清晰的路径。以下是经过 AgentScope 验证的**由浅入深设计经验**。

#### ① 文档的「漏斗式」层级

```
首页 Landing（1 页）—— 是什么？解决什么问题？
   ↓
快速开始 Quick Start（1~2 页）—— 5 分钟跑通最小示例
   ↓
核心概念 / 架构（概念级）—— 理解设计思想、核心抽象
   ↓
使用指南 / 专题（操作级）—— 按能力/场景深入（配置、API、进阶）
   ↓
参考 / FAQ / 迁移（兜底级）—— 类与配置参考、常见问题、升级指引
   ↓
案例 / 博客（场景级）—— 真实案例、最佳实践、发布说明
```

- **每级只回答一级问题**：概览页不堆细节，参考页不重复入门。
- **入口页用卡片/索引聚合**：如「概念页」用卡片列出各子主题并链到深入页面，读者按需点击。

#### ② 单页内部的结构化递进

每个文档页遵循「概览 → 上手 → 进阶 → 关联」的写作顺序：

| 段落 | 作用 |
| --- | --- |
| **Overview / 概览** | 先讲清楚「这个组件是什么、解决什么问题」，再进入细节 |
| **核心接口 / 主循环** | 展示最小可用形态（接口签名、主流程） |
| **配置 / Builder 字段** | 逐个字段说明，配示例代码 |
| **进阶能力** | 并发、中断、权限、持久化等高级话题 |
| **Next steps / Related pages** | 末尾给「下一步该看什么」的链接，引导路径延续 |

#### ③ 路径延续：每页必有「下一步」

- 每个页面结尾用 **Next steps / Related pages** 列出关联页面，形成可连续阅读的学习路径。
- 入口页（index / overview）用 **卡片组**（如 CardGroup）聚合所有子页面，一页即目录。

#### ④ 由浅入深的关键技巧

1. **先跑通再深入**：Quick Start 用最小依赖（core）而非全量功能，降低第一步成本。
2. **概念与操作分离**：架构/原理讲「为什么」，指南/专题讲「怎么做」。
3. **难度逐层递进**：基础用法 → 进阶用法（并发/容错/权限）→ 生产级（部署/运维）。
4. **交叉引用织网**：相关主题互相链接（如「模型集成」↔「模型扩展模块」），不重复撰写。
5. **案例放在最后**：等读者熟悉后，再用真实场景（客户案例、博客）强化认知。
6. **FAQ 兜底**：高频问题折叠在首页 + 完整 FAQ 页，减少读者卡点。

### 1.13 产品文档的方法论结构

当官网包含一个**产品/服务**（而非纯 SDK）时，产品文档有自己成熟的方法论结构。产品文档服务两类读者：**使用方**（怎么用）与**运维方**（怎么部署/维护），结构应同时覆盖两者。AgentScope Service 是典型示范（50 个页面）。

#### ① 产品文档的「四层框架」

```
① 产品概览（What is it?）    —— 产品是什么、解决什么问题、整体架构图
   ↓
② 快速开始（Quick Start）    —— 从安装到跑通第一次会话的完整流程
   ↓
③ 使用指南（How-to）         —— 按功能/对象拆分的操作手册（Agent/Team/Workflow/资源…）
   ↓
④ 运维与参考（Ops & Reference）—— 部署升级/故障排查 + API/SSE/配置参考
```

每层回答不同读者的问题：概览回答「值不值得用」，快速开始回答「怎么最快跑起来」，使用指南回答「每个功能怎么用」，运维参考回答「坏了怎么办」。

#### ② 按「对象」组织使用指南

产品文档通常**按核心对象/实体组织**，每个对象一套子页（能力/配置/执行/常见问题）：

```
对象A（如 Managed Agent）
├── 对象A 总览（是什么、适用场景）
├── 对象A 配置（如何创建/配置）
├── 对象A 执行（如何运行/调任务）
└── 对象A 能力/对比（支持哪些能力）
```

AgentScope Service 的三类 Agent 各有 `总览 + 配置 + 执行` 三件套（`managed-agent*`、`external-agent*`、`hosted-agent*`），Team、Workflow 等对象同理。

#### ③ 单页结构：场景驱动而非字段驱动

产品文档页面按「**用户场景/任务**」组织章节，而不是罗列配置字段。典型页面结构：

| 章节模式 | 示例（来自 agentscope） |
| --- | --- |
| **入口即选路** | 首页先讲「三种方式管理 Agent」（托管/外部/托管编码 Agent），让读者对号入座 |
| **In this chapter** | 章节开头的「本章包含」导航，给出完整路径 |
| **准备 → 创建 → 扩展 → 交付 → 运维** | `managed-agent.md`：Prepare → Add files → Extend capabilities → Delivery → Operate |
| **界面导览 + 动手** | `teams.md`：Interface tour → Create a team → Check readiness |
| **模式对比表** | `hosted-agent-providers.md`：能力对比表 |
| **概念图先行** | 首页/入口页先放架构图（mermaid），再分节解释 |

#### ④ 产品文档的运维闭环

产品文档必须覆盖「从上线到故障恢复」的全生命周期：

```
部署（quickstart/kubernetes）
→ 配置（configuration）
→ 运维（operations：备份/升级/恢复/回归验证）
→ 故障排查（troubleshooting：收集日志、逐症状诊断）
→ 发布（releasing）
```

#### ⑤ 产品文档与 SDK 文档的差异

| 维度 | SDK 文档 | 产品文档 |
| --- | --- | --- |
| 读者 | 开发者（写代码） | 使用者/管理员（用平台） |
| 组织单位 | 类/模块/API | 对象/功能/工作流 |
| 内容重心 | 接口签名、代码示例 | 界面操作、配置、流程、运维 |
| 结构驱动 | 代码驱动（按包/类） | 场景驱动（按任务/流程） |
| 示例形式 | 代码片段 | 操作步骤 + 截图 + 场景素材 |

## 2. 示范案例：AgentScope Java 官网

以下以开源项目 **AgentScope Java**（`https://github.com/agentscope-ai/agentscope-java`）的 `docs/` 目录为例，展示上一章节的结构在真实项目中的落地。

### 2.1 项目概览

| 项 | 说明 |
| --- | --- |
| 项目 | AgentScope Java（阿里开源的企业级多智能体框架） |
| 开源地址 | `https://github.com/agentscope-ai/agentscope-java` |
| 文档技术栈 | Mintlify（`mint` CLI）+ Markdown/MDX |
| 语言 | English（默认）+ 中文（zh） |
| 版本 | v1（历史）、v2（当前） |
| 运行要求 | Node.js >= 22 LTS，无需 Java/Maven |

### 2.2 文档库目录结构（真实截图）

```
docs/
├── docs.json              # 站点核心配置（导航/语言/版本/品牌/重定向）
├── package.json           # Node 依赖与脚本
├── landing.js             # 首页交互脚本（Tab 切换 / 代码复制）
├── style.css              # 自定义样式（.agentscope-landing 作用域）
├── logo.svg               # 站点 Logo
├── .mintignore            # 忽略文件
├── README.md              # 文档开发指南
├── scripts/               # 校验脚本（check-docs.mjs 等）+ 单元测试
├── examples/              # 示例代码
├── imgs/                  # 共享图片与截图
├── v1/                    # 历史版本
│   ├── en/{intro.md, blogs, community, docs, integration}
│   └── zh/{...}
└── v2/                    # 当前版本
    ├── en/{intro.md, blogs, community, docs, integration, service}
    └── zh/{...}
```

### 2.3 六大顶部 Tab（对应 1.1 的页面模块）

| Tab | 内容定位 | 对应核心模块 |
| --- | --- | --- |
| **Home / 首页** | 项目介绍、Landing 页 | 首页 |
| **SDK** | 快速开始、核心组件（Building Blocks）、Harness、参考 | 快速开始 + 指南 + 参考 |
| **Service / 服务** | 安装部署、Agent 管理、多 Agent 编排、场景案例、参考手册 | 使用手册 + 参考 |
| **Integration / 集成** | 模型提供商、记忆、状态存储、RAG、技能、协议、渠道、分布式存储 | 集成/生态 |

### 2.5 页面撰写规范（Front-matter）

每个页面以 YAML Front-matter 开头，`title` 为强制字段（校验脚本 `check-docs.mjs` 对缺 title 会报 `missing title`）：

- 普通页只需 `title`（建议补 `description`）。
- 首页用 `mode: custom` + `toc: false` 走自定义布局。

### 2.6 多语言与多版本维护

- **多语言**：`navigation.languages` 配 `en`（默认）与 `zh`；页面按 `v2/en/` 与 `v2/zh/` 平行存放，路径一一对应；Mintlify 按 URL 前缀提供语言切换。扩展新语种只需新增 `language` 条目 + 对应目录。
- **多版本**：`versions` 列出 `v2` 与 `v1`；v2 为主战场，v1 为历史快照；v1 下同样分 `en/zh` 双语对齐。

### 2.7 自定义交互与样式

- **`style.css`**：首页 Landing 的独立作用域样式，类名以 `.agentscope-landing` 前缀隔离，通过 CSS 变量定义主题（品牌色 `#0064FD` 等）。
- **`landing.js`**：首页交互——Tab 面板切换、代码复制（支持中英文提示、base64 内容），采用事件委托 + 全局单例保护。
- 首页效果示例：
  - 「Battle-tested in Production」为 `hs-adoption` 区块的静态文案 + CSS 呼吸动画，非真实数据源。
  - 底部集团/行业标签滚动为纯 CSS 跑马灯（`@keyframes` + `translateX(0 → -50%)` 双份内容无缝循环，悬停暂停，`prefers-reduced-motion` 降级）。
