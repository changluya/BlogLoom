# 全球 3D 访客地图核心 Demo 实现说明

> 核心代码：`global-visitor-globe.html`  
> 实现目标：在不依赖后端实时数据的前提下，验证全球访客地图的黑色地球、自动旋转、鼠标拖拽、滚轮缩放、国家与省州边界、中文国名、城市亮点及城市悬停交互。

---

## 一、背景与问题引入

### 1.1、为什么要做全球 3D 访客地图？

传统访客地图通常是“单一国家底图 + 城市散点”的二维展示。当目标扩展为“全球访客观测站”时，需要解决以下问题：

1. 原地图只能展示中国城市，不能表达全球访客分布。
2. 二维平面地图无法呈现“地球逐步点亮”的观测站氛围。
3. 仅有国界还不够，用户放大后希望看到类似中国省界的州、省、邦等一级行政区。
4. 城市名称不能和访客数据绑死：即使某个城市当前没有访客，也应能识别它的地理名称。
5. 全球边界数据量较大，如果每帧重复做坐标计算和文字排版，地球旋转会明显卡顿。

**核心目标：** 先交付一个数据可以是静态的 MVP，但地球、边界、城市与交互链路必须可用，后续只需替换访客统计数据源即可向真实产品演进。

### 1.2、MVP 需要回答哪些问题？

- 纯前端能否绘制可旋转的球面地图？
- 中国能否保持既定的省级边界与视觉表达？
- 其他国家能否展示州、省、邦边界？
- 国家名、行政区名和城市名如何避免彼此重叠？
- 没有访客数据的城市如何参与悬停命中？
- 在加入全球 ADM1 数据后，如何保证旋转流畅？

## 二、核心概念与技术栈

### 2.1、什么是 ADM0 和 ADM1？

| 层级 | 含义 | Demo 中的用途 |
| --- | --- | --- |
| ADM0 | 国家/地区边界 | 绘制全球国界和国家底色 |
| ADM1 | 一级行政区 | 绘制美国州、日本都道府县、印度邦、澳大利亚州等 |
| 城市点位 | 城市中心的经纬度 | 悬停识别、访客亮点和点击聚焦 |

**重点：** 当前中国蓝色内部线是省级边界，不是全国所有城市行政区边界。因此，其他国家与中国对齐的第一步应该是 ADM1，而不是一次加载全球 ADM2/ADM3。

### 2.4、PV 和 UV 分别是什么？

#### PV（Page View，页面访问量）

PV 表示页面或被统计访问事件发生的总次数。同一个访客在统计周期内访问 5 个页面，会产生 5 PV。

实现前必须先明确哪些 URI 或用户行为计入 PV。如果直接将所有服务端请求当作 PV，数值可能同时包含页面浏览、资源请求和接口调用，从而失去业务含义。

#### UV（Unique Visitor，独立访客数）

UV 表示统计周期内去重后的访客数。同一个访客无论访问多少个页面，在同一统计周期内通常只计为 1 UV。

UV 需要选定稳定的访客去重键，例如匿名访客 ID、登录用户 ID 或符合隐私规范的设备标识。浏览器/设备标识不等于严格意义上的真实自然人；清除标识、更换设备或使用多个浏览器都可能影响 UV。

#### PV 与 UV 的示例

| 访客 | 周期内访问次数 | PV 贡献 | UV 贡献 |
| --- | ---: | ---: | ---: |
| 访客 A | 5 | 5 | 1 |
| 访客 B | 2 | 2 | 1 |
| 合计 | 7 | 7 | 2 |

**重点：** PV 通常可以在不同城市或时间段之间直接求和；UV 不能在所有场景下直接相加。同一 UUID 在同一天访问了北京和上海时，两个城市可能各有 1 UV，但全球总 UV 仍只是 1。总 UV 应从原始去重键计算，不应简单将城市 UV 求和。

### 2.5、城市 PV、国家码、经纬度和统计周期是什么？

| 名词 | 定义 | 在全球访客地图中的作用 | 实现条件 |
| --- | --- | --- | --- |
| 城市 PV | 某个统计周期内，定位到某城市的访问事件总次数 | 用于城市详情、排名和热度强度 | 访问事件必须包含事件时间并可关联到标准城市 |
| 城市 UV | 某周期内定位到某城市的去重访客数 | 用于城市热点和 Top 20 排名 | 必须按“统计周期 + 城市 + 访客标识”去重 |
| 国家码 | 国家/地区的稳定标识，推荐使用 ISO 3166-1 Alpha-2，如 `CN`、`US`、`JP` | 稳定关联国家边界、翻译名称和访客统计 | IP 解析或地理维表必须输出标准国家码 |
| `mapId` | 当前地图数据中的数字国家 ID，如中国 `156` | 将统计数据关联到 ECharts/world-atlas 多边形 | Demo 中使用，正式接口可由前端地理维表转换，不必强制后端返回 |
| 经度 `lng` | 地球东西方向坐标，范围通常为 `-180～180` | 决定城市点在球面上的水平位置 | 当前可从本地城市坐标字典补充，IP 库不直接返回 |
| 纬度 `lat` | 地球南北方向坐标，范围通常为 `-90～90` | 决定城市点在球面上的垂直位置 | 与经度相同，需通过城市地理维表补充 |
| 统计周期 | 一次聚合覆盖的时间窗口，例如自然日、最近 24 小时、自然周或自然月 | 决定数据卡片、排名和点亮效果在表达哪段时间 | 数据必须同时提供周期类型、开始时间和结束时间 |
| 时区 | 将时间戳划分到自然日/周/月时使用的时区 | 保证“今日”、“24h”与运营口径一致 | 聚合程序、数据库与前端必须使用明确且一致的时区 |

**注意：** 地图中的经纬度是城市中心或代表点，不是访客的精确住址。IP 定位本身存在误差，展示时应保持城市/区域级精度，不应误导为精确点位。

### 2.6、统计周期应如何定义？

“今日”与“最近 24 小时”不是同一个口径：

| 周期 | 示例 | 特点 |
| --- | --- | --- |
| 自然日 | 亚洲/上海时区当日 `00:00～24:00` | 适合日报和运营口径，零点清零 |
| 最近 24 小时 | 当前时刻向前滚动 24 小时 | 适合右上角 `24h` 实时观测，不在零点突然清零 |
| 自然周 | 周一 `00:00` 至下周一 `00:00` | 适合周报和跨天排名 |
| 自然月 | 每月 1 日至下月 1 日 | 适合月度趋势和长期地域分布 |

推荐每份聚合数据明确携带 `periodType`、`periodStart`、`periodEnd` 和 `timezone`，避免前端只看到一个数值，却无法判断它是当日、累计还是最近 24 小时。

## 三、技术方案对比

### 3.1、如何选择地球渲染方案？

#### 方案一：ECharts 二维世界地图

**优点：** 地图、散点和 Tooltip 开发成本低，适合已使用 ECharts 的前端工程。

**弊端说明：** ECharts 4 普通 `geo/map` 是平面投影，不能直接实现球体旋转和地球背面遮挡。

**适用场景：** 保留历史二维仪表盘，不适合本次核心 Demo。

#### 方案二：Three.js + Globe.gl

**优点：** 基于 WebGL，球体、大气层、立体多边形、飞线和镜头控制效果好，后续扩展空间轨迹更方便。

**弊端说明：** 即使已改为本地静态资源，WebGL 路径仍需更高的 GPU 与显存资源，且当前尚未完整复刻 Canvas 路径的 ADM1 和无访客城市功能。

**适用场景：** 正式版在依赖本地化后的优选方案。

#### 方案三：原生 Canvas 球面投影

**优点：** 无额外运行时依赖，本地 `file://` 直接打开也可渲染，数据和图层完全可控。

**弊端说明：** 需自行处理投影、背面剔除、多边形路径、文字避让、命中检测和性能优化。

**适用场景：** 离线 MVP、技术可行性验证和 CDN 失败时的稳定兜底。

### 3.2、当前 Demo 的选择

Demo 只保留经过完整验证的 Canvas 展示路径：

```javascript
const rendererMode = 'canvas';
mountFallbackGlobe();
```

**重点：** Canvas 路径已完整支持中国版图、海外 ADM1、中文国名与无访客城市命中。为了只保留效果展示所需资源，核心包不再附带 WebGL 依赖、地球纹理和 ADM1 原始源文件。

## 四、核心实现思路

### 4.1、如何把平面经纬度投影到可旋转球面？

对于经度 `lng`、纬度 `lat`，先转换为三维单位球坐标：

```text
x = cos(lat) * sin(lng)
y = sin(lat)
z = cos(lat) * cos(lng)
```

再使用 `yaw` 控制水平旋转，使用 `pitch` 控制垂直倾斜，最后把旋转后的 `x/y` 映射到 Canvas 屏幕坐标。

`rotatedZ <= 0` 表示地球背面，该点不绘制，从而实现球体遮挡效果。

### 4.2、如何保持中国版图的独立表达？

Demo 没有用第三方全球数据覆盖中国，而是单独加载：

```html
<script src="/static/echarts/map/js/china.js"></script>
<script src="/static/echarts/map/js/world.js"></script>
```

处理流程如下：

1. 用 ECharts `getMap('china')` 读取本地中国 GeoJSON。
2. 解码 ECharts 4 的 UTF8 压缩坐标。
3. 从全球 `world.js` 中排除 China，避免两套中国边界重叠。
4. 最后单独绘制 `china.js` 的省级边界，并使用紫色填充和 `#389dff` 蓝色描边。

**注意：** 中国地图数据的版本、边界口径和审图要求应在正式上线前单独进行合规审核。

### 4.3、其他国家如何获得类似中国的内部边界？

当前 MVP 下载了以下 10 个国家的 geoBoundaries gbOpen ADM1 数据：

| ISO3 | 国家 | 对应 ADM1 |
| --- | --- | --- |
| USA | 美国 | 州等 |
| CAN | 加拿大 | 省和地区 |
| AUS | 澳大利亚 | 州和领地 |
| BRA | 巴西 | 州 |
| FRA | 法国 | 大区 |
| DEU | 德国 | 联邦州 |
| IND | 印度 | 邦和中央直辖区 |
| JPN | 日本 | 都道府县 |
| GBR | 英国 | 一级行政区 |
| SGP | 新加坡 | 一级统计/行政区 |

上述数据共包含 226 个 ADM1 区域。Canvas 按国家使用不同色调绘制内部边界，默认全球视图即可看到；放大到 `zoom >= 1.45` 并暂停旋转后，还会显示州、省、邦名称。

页面仅保留约 312KB 的 `data/adm1-mvp.js` 简化结果。约 46MB 的原始 simplified GeoJSON 不属于页面运行时依赖，因此不放入核心展示包。

### 4.4、ADM1 数据如何压缩？

处理脚本包含四个步骤：

1. 读取各国 GeoJSON。
2. 使用 Douglas-Peucker 思路删除对边界形状影响较小的中间点。
3. 针对加拿大、澳大利亚等多岛国家过滤地球全景下无法识别的极小外岛环。
4. 将坐标保留三位小数，并计算行政区标签中心。

**重点：** 源数据与渲染数据分开管理。核心 Demo 只交付简化后的渲染结果，避免浏览器和代码包承担几十 MB 的边界源数据。

### 4.5、国家名和行政区名如何显示？

- `countryLabels` 维护大国中文名称及标签经纬度，在国家位于地球正面时默认绘制。
- 标签使用深色 `strokeText` 描边和浅色 `fillText` 填充，保证在深色地图上可读。
- 每个文字标签计算屏幕矩形，与已绘制矩形重叠时跳过，避免密集覆盖。
- ADM1 名称只在放大到 `zoom >= 1.45`、且暂停自动旋转时显示，避免旋转过程中每帧进行大量 `measureText` 和冲突检测。

右上角提供“中文 / EN”切换。语言状态会直接参与 Canvas 每帧绘制，因此地球上的国家名、发光城市名、城市悬停提示与右侧热点排名会同步切换，不需要重新加载页面。

### 4.6、城市数据为什么要拆成两层？

```javascript
const staticCities = [
  { city: '北京市', lat: 39.91, lng: 116.41, uv: 520, pv: 1280 }
];

const referenceCities = [
  { city: '重庆市', country: '中国', lat: 29.57, lng: 106.56 }
];
```

- `staticCities` 是访客统计层，只包含需要发光、波纹和展示 UV/PV 的城市。
- `referenceCities` 是地理名称层，即使没有访客也可参与鼠标命中。
- `visitorStatsByCity` 将两层关联。命中城市后，有统计则显示访客数，无统计则显示“暂无访客统计”。

这个拆分避免了一个常见问题：不能因为某城市 UV 为 0，就认为该城市在地理上不存在。

### 4.7、鼠标拖拽、缩放和点击如何实现？

| 交互 | 事件 | 状态变化 |
| --- | --- | --- |
| 开始拖拽 | `pointerdown` | `drag = true`，记录起始坐标 |
| 拖动地球 | `pointermove` | 根据 `dx/dy` 更新 `yaw/pitch` |
| 结束拖拽 | `pointerup` | 区分拖拽和点击，点击时查找最近城市 |
| 滚轮缩放 | `wheel` | 将 `zoom` 限制在 `0.72～2.25` |
| 暂停旋转 | `click` | 切换 `autoRotate` |
| 重置视角 | `click` | 恢复中国附近默认角度和缩放比 |

### 4.8、如何保证旋转流畅？

#### 优化一：绘制数据预简化

ADM1 源数据约 46MB，渲染包压缩到约 312KB，将每帧遍历的边界点数控制在可接受范围。

#### 优化二：缓存单位球坐标

旧方式会在每一帧、每一个边界点上重复调用 `sin/cos`。当前代码第一次遇到坐标时计算 `_sphere`，后续旋转只做矩阵换算：

```javascript
if (!coordinate._sphere) {
  coordinate._sphere = [unitX, unitY, unitZ];
}
return projectUnit(coordinate._sphere);
```

#### 优化三：每帧只计算一次视角参数

`yawCos/yawSin/pitchCos/pitchSin`、球心和半径由 `updateProjectionFrame()` 每帧统一计算，所有地理点共享。

#### 优化四：浏览器原生帧同步

使用 `requestAnimationFrame(draw)` 跟随浏览器刷新，不再人为限制为约 30FPS。旋转速度也从“每帧 0.0048”调整为“每帧 0.0024”，保持 60FPS 下的视觉速度接近原设计。

#### 优化五：动态降级文字层

自动旋转时保留国界、ADM1 线和大国中文名，暂停旋转且放大后才排版大量州/省名，优先保证连续旋转。

**注意：** Canvas 像素比上限为 1，这是流畅度与高分屏锐利度的取舍。如果正式版改用 WebGL，可在 GPU 压力可控的前提下恢复更高 DPR。

### 5.2、如何运行 Demo？

Demo 引用本地 ECharts 和地图 JS，因此需保持目录相对关系。可以直接用 Chrome 打开：

```bash
open -a "Google Chrome" \
  "docs/工程化开发模块设计思路产物/backend/核心迭代功能设计/后台功能/访客地图/核心demo/global-visitor-globe.html"
```

页面固定使用功能完整的 Canvas 路径，不需要下载或加载 WebGL 静态资源。

### 5.3、首屏绘制顺序

Canvas 每帧使用固定的图层顺序：

```javascript
drawGrid();
drawWorldMap();
drawGlobalAdm1();
drawChinaMap();
drawCountryLabels();
drawCountryLights();
drawCityPoints();
```

这个顺序的原因是：

1. 经纬网和全球国界作为底层。
2. 海外 ADM1 叠加在国家底图上。
3. 中国版图后画，保证独立省界数据不被全球数据覆盖。
4. 国名、光晕和城市点位最后绘制，保证信息可读。

### 5.4、如何替换为真实后端数据？

当前 `data.json` 是全球访客统计的唯一可编辑源数据，包含 `meta`、`summary`、`countries` 和 `cities` 四个部分。它同时是未来全球接口的结构样例：

```json
{
  "meta": {
    "periodType": "rolling_24h",
    "periodStart": "2026-10-16T10:40:00+08:00",
    "periodEnd": "2026-10-17T10:40:00+08:00",
    "timezone": "Asia/Shanghai",
    "coordinateSystem": "WGS84"
  },
  "summary": {"uv": 6789, "pv": 16188, "countryCount": 19, "cityCount": 40},
  "countries": [
    {"countryCode": "CN", "mapId": "156", "country": "中国", "lat": 35, "lng": 103, "uv": 3927, "pv": 9450}
  ],
  "cities": [
    {
      "cityCode": "CN-BJ",
      "city": "北京市",
      "countryCode": "CN",
      "lat": 39.910925,
      "lng": 116.413384,
      "uv": 520,
      "pv": 1280,
      "accuracyKm": 50
    }
  ]
}
```

修改 `data.json` 后执行：

```bash
node scripts/build-visitor-data.js
```

脚本会验证城市 PV 之和与 `summary.pv` 是否一致，并验证全球 UV 不大于城市 UV 合计，然后生成 `data/visitor-stats.js`。不强制全球 UV 等于城市 UV 之和，因为同一访客可能在同一周期内出现于多个城市。生成 JS 只是为了兼容直接双击 HTML 时的 `file://` 限制，不是第二份手工数据源。

### 5.5、一份合格的全球统计数据需要满足什么条件？

只有全球 PV/UV 总数不足以驱动地图。数据集必须同时具备“可定位、可聚合、可解释、可关联”四项能力：

| 条件 | 必需内容 | 原因 |
| --- | --- | --- |
| 可定位 | 标准国家码、城市代码、经纬度 | 将统计值放到正确的国家边界和城市点上 |
| 可聚合 | 访问事件、访客去重键、事件时间 | 分别计算 PV 和 UV，并能按国家或城市分组 |
| 可解释 | 周期类型、开始时间、结束时间、时区 | 避免将“今日”、“最近 24 小时”和“历史累计”混为一谈 |
| 可关联 | 统计数据和地理边界共用的稳定 ID | 避免依赖多语言名称或模糊字符串匹配 |

**最小可用结论：** 国家和城市两级都应提供 UV/PV、标准代码与统计周期；城市级还必须提供经纬度或可关联到经纬度的稳定城市 ID。

### 5.7、为达到目标需要哪些数据？

数据可以分为四层：

```text
原始访问事实
  visitorId + ip + eventTime + 访问事件
                 │
                 ▼
地理标准化
  countryCode + regionCode + cityCode + 标准名称 + lat/lng
                 │
                 ▼
周期聚合
  periodType/start/end/timezone + 国家/城市 PV/UV
                 │
                 ▼
前端渲染数据
  summary + countries[] + cities[] + 独立地名层
```

| 数据层 | 最小字段 | 作用 | 当前来源 |
| --- | --- | --- | --- |
| 原始访问事实 | `visitorId`、`ip`、`eventTime`、访问事件 | 计算 PV、按访客标识去重计算 UV | 访问日志或埋点系统 |
| 国家维度 | `countryCode`、`countryName`、`mapId` | 关联国家多边形、中文名和排名 | ISO 国家码与地理维表 |
| 城市维度 | `cityCode`、`cityName`、`countryCode`、`lat`、`lng` | 稳定关联城市、绘制点位和悬停命中 | 全球城市地理维表 |
| 周期定义 | `periodType`、`periodStart`、`periodEnd`、`timezone` | 确定统计时间口径 | 聚合任务或统计接口 |
| 国家聚合 | `countryCode`、`pv`、`uv` | 国家点亮和国家级热度 | 按周期和国家分组聚合 |
| 城市聚合 | `cityCode`、`countryCode`、`pv`、`uv` | 城市亮点、Tooltip 和 Top 20 | 按周期和城市分组聚合 |

### 5.8、前端最终需要哪些渲染字段？

| JSON 路径 | 必填 | 作用 |
| --- | --- | --- |
| `meta.periodType` | 是 | 标识 `rolling_24h`、`day`、`week`、`month` 等统计口径 |
| `meta.periodStart/periodEnd` | 是 | 明确统计窗口的开始与结束时间 |
| `meta.timezone` | 是 | 解释时间边界，如 `Asia/Shanghai` |
| `meta.coordinateSystem` | 是 | 声明经纬度坐标系，Demo 使用 `WGS84` |
| `summary.pv/uv` | 是 | 右上角全球汇总卡片 |
| `summary.countryCount/cityCount` | 是 | 点亮国家和城市热点数量 |
| `countries[].countryCode` | 是 | 业务统计与地理维度的稳定关联键 |
| `countries[].mapId` | Demo 需要 | 关联当前 ECharts/world-atlas 国家多边形 |
| `countries[].country/lat/lng` | 是 | 显示国名并定位国家光晕/标签 |
| `countries[].pv/uv` | 是 | 计算国家热度和国家级统计 |
| `cities[].cityCode/countryCode` | 是 | 稳定识别城市及区分中国/国外 |
| `cities[].city/lat/lng` | 是 | 绘制城市点、标签和鼠标命中 |
| `cities[].pv/uv` | 是 | 显示访问强度、Tooltip 和城市排名 |
| `cities[].accuracyKm` | 否 | 表达 IP 定位的大致误差或数据精度 |

**重点：** 地图边界数据（ADM0/ADM1）与访客统计数据是两类数据。边界数据负责“画在哪里”，访客数据负责“点亮谁、点多亮、排第几”，两者通过国家码、城市代码和经纬度关联。

替换时保持三个原则：

1. 后端返回 ISO 国家码或内部稳定 ID，不要仅用国家中文名关联地图。
2. 城市返回标准化经纬度，不要让前端再使用城市字符串猜坐标。
3. 地名层与访客统计层继续分离，不要用 UV 是否大于 0 决定城市是否存在。

## 六、数据来源与口径

### 6.1、全球国家边界

Canvas 路径使用本地 ECharts 4.9.0 的 `echarts/map/js/world.js`。该数据经过 ECharts UTF8 坐标编码，Demo 通过 `decodeEchartsGeoJson()` 恢复经纬度。

精简版不再附带第二套 WebGL 国家边界数据，避免重复地理数据增加交付体积。

### 6.2、中国省级边界

来源是本地 `echarts/map/js/china.js`。中国边界与全球国家边界分开管理，便于锁定版本、单独更新和进行合规审核。

### 6.3、海外州/省/邦边界

来源是 geoBoundaries `gbOpen` ADM1。geoBoundaries API 使用 ISO3 国家码与 ADM 层级返回对应数据的完整版和简化版下载地址。

**许可说明：** gbOpen 整体按 CC BY 4.0 提供，使用时需保留归属说明；各国源数据的详细许可和原始来源应以 geoBoundaries API 元数据为准。

### 6.4、城市坐标

- 中国主要城市坐标由本地城市地理维表提供。
- 海外城市在 MVP 中是手工维护的静态样例点。
- 当前经纬度用于视觉验证，不代表 IP 定位能达到城市中心级精度。

### 6.5、访客数据

`data.json` 中 `countries` 和 `cities` 的 UV/PV 均是 Demo 静态数据，用于验证国家点亮、城市排名和光晕强度。右上角将城市分为“中国”与“国外”两组，每组按 UV 降序展示 Top 20，两个列表均可独立纵向滚动。

**注意：** 这些数值是功能演示数据，不是生产统计，不应用于业务分析结论。

## 八、已知限制与后续演进

### 8.1、当前已知限制

1. 访客 UV/PV 是静态样例，尚未对接真实的全球访问事件与聚合数据源。
2. 海外 ADM1 目前只覆盖 10 个 MVP 国家，不是全球所有国家。
3. ADM1 名称大部分保留源数据语言，尚未建立全球中文翻译表。
4. 城市命中当前是“屏幕最近点”，不是城市行政区多边形命中。
5. Canvas 路径是 3D 视觉投影，不是具有深度缓冲、摄像机和着色器的真 WebGL 场景。
6. 精简展示包不包含 WebGL 渲染路径，若未来需要真实立体场景，应在正式前端工程中另行引入。

### 8.2、后续建议

1. 如需 WebGL，在正式前端工程中按需引入，并迁移 Canvas 已验证的 ADM1、中文国名和城市地名层。
2. 对新增依赖进行包体积预算、版本锁定和 LICENSE 校验。
3. 后端增加国家、行政区、城市和时间维度的标准化聚合表。
4. 使用 ISO 3166-1/3166-2 或项目自有地理 ID，解决多语言名称不稳定问题。
5. 增加按需加载：转到某个国家或缩放达到阈值后，再加载该国 ADM1/ADM2。
6. 增加性能采样和降级策略：低端设备减少边界精度、关闭城市波纹或限制标签数。
7. 正式上线前完成边界数据口径、归属、隐私与 IP 地理定位合规审核。

## 九、总结

`global-visitor-globe.html` 已经完成了从“中国二维访客地图”到“全球可旋转访客地球”的核心技术验证：

- 中国使用独立管理的省级边界数据。
- 全球国界、大国中文名和城市亮点可同时展示。
- 海外 10 个重点国家已接入 226 个 ADM1 内部区域。
- 城市地名层与访客统计层已解耦。
- 右上角中英文切换可同步更新地球国名、城市名、悬停提示和排行榜。
- 通过离线数据简化、球面坐标缓存、文字动态降级和 `requestAnimationFrame`，保证地球旋转的基本流畅度。

这版 Demo 的价值不是直接作为生产代码，而是已经打通“全球边界 → 球面投影 → 省州分层 → 城市亮点 → 交互命中 → 性能优化”的技术链路。后续只需按本文定义的字段和统计口径对接真实全球访客数据。
