# 历史存量访客地图设计

## 一、历史背景设计与现状拆解

> 调研分支：`feat_1.0.x_9`<br />
> 调研日期：2026-10-16<br />
> 本章只记录现有访客地图的历史来源、技术栈、数据链路和可继续演进的边界；全球化、3D 化的详细落地方案另行设计。

### 1.1 历史来源与演进结论

BlogLoom 的后台访客地图不是从零设计的独立全球地图，而是沿用了 Naccl/NBlog 的“中国城市访客分布”方案。项目 README 明确说明 BlogLoom 基于 Naccl/NBlog 二次开发；当前仓库初始提交 `f785762` 已包含仪表盘地图、`city_visitor` 表、`VisitorSyncScheduleTask` 和 `city2coord.json`，说明这套地图属于项目继承的存量能力。

从 Git 历史看，演进关系如下：

| 阶段 | 代码事实 | 对地图的影响 |
| --- | --- | --- |
| NBlog 基础方案 | 后端以 `Visitor`、`VisitLog`、`VisitRecord`、`CityVisitor` 记录访问数据，前端使用中国地图 + 城市散点 | 形成当前地图的数据模型和交互样式 |
| BlogLoom 初始提交 `f785762` | 保留原有地图渲染逻辑和城市坐标文件 | 地图仍然是中国范围，按城市 UV 展示 |
| 包名与产品迁移 `4babb0a` | `top.naccl` 迁移为 `com.changlu.blogloom`，同时进行后台布局改造 | 地图算法未发生方向性变化 |
| 仪表盘聚合改造 `9d0dd4d` | 分类、标签改为 SQL 聚合，访客地图仍复用原 `cityVisitor` 数据 | 地图仍是存量方案，并未升级为实时或全球地图 |

因此，当前地图的设计原点可以概括为：

> 用离线 IP 库把访问者 IP 解析为中国城市；每天凌晨把“昨日新增访客”的城市 UV 累加到城市汇总表；后台仪表盘读取城市汇总并在中国地图上绘制普通散点和 Top 5 动效散点。

这里的“历史存量”是指已有的累计城市访客数据和已有的访问日志，不是已经具备按日期回放能力的历史地图快照。`city_visitor` 没有日期字段，当前只能表达“累计到当前的城市 UV”，不能直接还原某一天地图的状态。

### 1.2 前端访客地图组件技术栈

访客地图位于 `blog-cms-ui/src/views/dashboard/index.vue`，依赖关系如下：

| 层次 | 当前实现 | 说明 |
| --- | --- | --- |
| 前端框架 | Vue `2.6.11` | 单文件组件，生命周期中请求数据、初始化和销毁图表 |
| 构建工具 | Vite `4.5.14` | CMS 前端构建与开发服务 |
| 图表引擎 | ECharts `4.9.0` | 负责地图底图、地理坐标系、散点、动效和 Tooltip |
| 地图底图 | `echarts/map/js/china` | ECharts 4.x 内置中国地图数据，`map: "china"` 注册并使用 |
| 坐标字典 | `src/util/city2coord.json` | 城市名称到 `[经度, 纬度]` 的本地映射，来源注释指向 `Naccl/region2coord` |
| 页面容器 | Element UI `2.13.2` | `el-row`、`el-col`、`el-card` 等负责布局，不负责地图绘制 |
| 图形渲染器 | ECharts 默认 Canvas | 代码调用 `echarts.init(dom)`，没有指定 `renderer: 'svg'` |

ECharts 的 `geo` 坐标系可以承载 `scatter`、`effectScatter`、`lines` 等系列；当前代码使用 `geo + map + scatter + effectScatter`。页面通过 `GET /admin/dashboard` 获取 PV、UV、趋势和 `cityVisitor`；前端用城市名查 `city2coord.json` 换成 `[longitude, latitude]`，全量点使用 `scatter`，UV 排名前 5 使用 `effectScatter` 展示波纹与城市名。普通点和 Top 5 点的大小是固定值，UV 主要出现在 Tooltip 中，因此现有效果是城市分布加 Top 5 突出，不是按值连续变化的热力图。组件在 `mounted` 请求并初始化，在 `beforeDestroy` 释放 ECharts，不进行 WebSocket、SSE 或定时轮询。

### 1.3 PV 如何采集和统计

`@VisitLogger` 标记的接口在业务方法正常返回后，由 `VisitLogAspect` 创建访问日志。`VisitLogServiceImpl` 补充 ip2region 地域、操作系统和浏览器信息，再通过异步方式写入 `visit_log`；因此这里的 PV 口径是被埋点的请求次数，并不是浏览器内每次页面渲染的通用统计。异步写入也意味着新访问可能会在一小段时间后才反映到今日 PV 查询中。

| 时效/用途 | 实现口径 | 涉及表及字段 |
| --- | --- | --- |
| 今日 PV | `/admin/dashboard` 执行 `count(*)` 统计 `visit_log` 中 `date(create_time)=curdate()` 的行数 | `visit_log`: 每次访问一行；核心字段有 `uuid`、`uri`、`method`、`ip`、`ip_source` 和 `create_time` |
| 历史每日 PV | 每日任务查出昨日 `visit_log` 行，行数就是昨日 PV，写入一条每日聚合记录 | `visit_record`: `pv`、`uv`、`date` |
| 单访客累计 PV | 任务按昨日每个 UUID 的日志行数更新访客档案 | `visitor`: 一个 UUID 档案一行，核心字段有 `uuid` 、`create_time` 、`last_time` 、`pv` |

完整链路：

```text
@VisitLogger 接口正常返回
  → VisitLogAspect 组装访问明细
  → VisitLogServiceImpl 解析 ip_source / OS / Browser
  → visit_log（每个被记录的请求一行）
      ├→ 当日 count(*) → /admin/dashboard.pv
      └→ 次日聚合 PV → visit_record.pv
                         └→ 按 UUID 累加到 visitor.pv
```

### 1.4 UV 如何识别和统计

`VisitLogAspect` 用请求头 `identification` 识别站点访客。如果没有该头，后端以小时时间戳 + IP + User-Agent 生成 UUID，写入响应头供前端后续请求携带；对已有 UUID，系统先查缓存集合，未命中再查 `visitor.uuid`，存在则恢复到缓存，不存在则签发新 UUID。首次访客档案保存到 `visitor`，包含 UUID、IP 地域、设备/浏览器和首次/最后访问时间。

| 时效/用途 | 实现口径 | 涉及存储及字段 |
| --- | --- | --- |
| 当前 UV | `/admin/dashboard` 统计当前 `identificationSet` 中的成员数，每个 UUID 只占一个集合成员 | MySQL `cache_entry`: `cache_key` 是 `identificationSet:<uuid>`，`cache_value` 保存成员值；`visitor.uuid` 保存持久化访客档案 |
| 历史每日 UV | 每日任务以昨日 `visit_log` 为准，将所有日志按 UUID 去重；去重后数量写入 `visit_record.uv` | `visit_log.uuid` + `visit_log.create_time` 计算；`visit_record`: `uv`、`date` |
| 城市地图 UV | 任务查出昨日首次创建的 `visitor` 档案，仅汇总国家字段为“中国”且含城市字段的记录；兼容旧四段和新五段地域文本，取第 3 段城市名累加到 `city_visitor.uv` | `visitor`: `uuid` 、`create_time` 、`ip_source` → `city_visitor`: `city` 主键、`uv` 累计值 |

```text
identification 请求头（无则按小时时间戳 + IP + UA 签发 UUID）
  ├→ cache_entry: identificationSet:<uuid> → 去重并计算当前 UV
  └→ visitor（一 UUID 档案，首次地域和设备信息）
       ├→ 昨日 visit_log.uuid 去重 → visit_record.uv（每日 UV）
       └→ 昨日新增档案中的中国城市 → city_visitor.uv（城市累计值）
```

**口径注意：** `city_visitor.uv` 是按日累加的新建访客 UUID 数，不是有日期维度的城市日 UV。新 UUID 使用小时时间戳 + IP + User-Agent 构造；如果客户端没有持续携带服务端回传的 `identification`，跨小时可能会生成新 UUID。UV 反映站点的访客标识口径，不等于真实自然人数。每日任务会先清理 `identificationSet`，当日的请求再逐步重建该集合；历史每日 UV 从 `visit_log` 重算，不依赖已清理的缓存集合。

### 1.5 面向“全球博客观测站”的现状差距

基于当前实现，可以确认“做成全球博客观测站”在技术上可行，但不能通过简单替换中国地图文件完成。当前存量方案至少存在以下边界：

1. **空间范围受限**：任务代码明确只处理 `ip_source` 以“中国”开头的记录；坐标文件是面向 ip2region 城市字段的中国城市字典，约 362 个城市，不是全球城市字典。
2. **地图底图受限**：前端同时使用 `map: "china"` 和中国 GeoJSON，换成全球需要新的全球边界数据与国家/地区标准化策略。
3. **统计时间受限**：`city_visitor` 没有日期，数据是累计加和；无法按日、周、月回放全球访客迁移轨迹。
4. **实时性不足**：地图数据按日凌晨更新；“访客地域实时分布”是产品文案，不代表地图接口实时返回访问流。
5. **地域粒度受限**：当前城市名既是展示名也是主键，没有国家码、行政区码和经纬度快照；同名城市、名称变化、不同语言名称都无法稳定关联。
6. **异常数据不可见**：城市坐标缺失时前端静默跳过；当前接口没有返回“无法定位、无法匹配坐标、被过滤”的数量。
7. **隐私与合规需要单独评审**：系统持久化 IP、User-Agent 和地域信息；全球化后应增加数据最小化、保留期限、匿名化/哈希化、地区化存储和用户告知等设计，不能直接照搬现有明文存储口径。

### 1.6 本章结论

当前访客地图可以准确地定义为：

> 基于 Vue 2 + ECharts 4.9 的二维中国城市访客累计分布图；数据由 ip2region 离线解析 IP，每日从新增访客中聚合城市 UV，后端通过 `city_visitor` 返回，前端用本地城市坐标字典转换后，以 `scatter` 和 `effectScatter` 绘制。

它已经具备后续升级的三个可复用基础：

- 访问明细：`visit_log` 可以作为全球化聚合的事实来源；
- 访客档案：`visitor` 可以继续承载 UUID、首次访问和设备信息；
- 仪表盘通道：`/admin/dashboard` 已有统一的数据返回入口。

但要落地全球化和 3D 化，后续方案至少需要把“国家/地区/城市标准化、全球底图、按时间聚合、实时或准实时刷新、隐私治理”从现有的字符串和累计表中拆出来，新增独立的地理维度与时间聚合模型。本章不把这些未来设计误认为当前已有能力。

### 1.7 前后端地域字典与地图页面渲染流程

#### 1.7.1 后端 IP 地域字典：ip2region

##### 1.7.1.1 ip2region 开源项目简介

ip2region 是一个开源的离线 IP 地域查询库及数据管理框架，提供查询客户端和 `.xdb` 数据生成工具。上游提供 IPv4、IPv6 的原始 IP 段数据及对应数据库文件，标准地域结果字段为“国家|省/州|城市|运营商|ISO 两位国家码”；中国地域信息使用中文，非中国地域信息使用英文。因此，**ip2region 上游项目面向全球 IP 地域查询，不是中国专用库**。[官方项目说明](https://github.com/lionsoul2014/ip2region)

这里的“全球”表示数据尝试覆盖多个国家和地区，并不代表所有 IP 都能稳定解析到城市：IP 定位是近似地域，粒度和准确度取决于数据记录；上游开源数据不定期更新。对更新频率或精度有较高要求时，需要评估持续维护数据或商业数据方案。

**与 BlogLoom 当前能力的区别：** 后端现已加载官方 IPv4、IPv6 两份 XDB 并由统一查询服务自动路由，IP 地域查询具备全球数据覆盖基础；这不等于访客地图已全球化。当前城市 UV 聚合仍只统计中国记录，前端城市坐标字典也只覆盖中国城市，因此现有地图仍未实现全球城市统计与展示。

##### 1.7.1.2 当前仓库的数据文件与集成方式

后端使用 [IPv4 数据文件 `ip2region_v4.xdb`](../../../../../../blog-backend/src/main/resources/ipdb/ip2region_v4.xdb) 和 [IPv6 数据文件 `ip2region_v6.xdb`](../../../../../../blog-backend/src/main/resources/ipdb/ip2region_v6.xdb)。[`IpAddressUtils`](../../../../../../blog-backend/src/main/java/com/changlu/blogloom/util/IpAddressUtils.java) 在服务启动时从 classpath 加载两份文件，`org.lionsoul:ip2region:3.3.7` 的统一 `Ip2Region` 服务自动识别请求 IP 版本并查询对应数据。当前使用全量内存缓存，两份数据合计约 47 MB，会随后端 JAR 一起打包并在启动时载入内存。

新地域结果采用 `Country|Province|City|ISP|ISO-Alpha2` 五段格式，例如：

```text
中国|广东省|深圳市|电信|CN
```

**数据文件从哪里来：** `.xdb` 是 ip2region 上游生成并发布的离线数据库文件，不是 BlogLoom 在启动时生成或下载的。上游提供 IP 段原始数据及 `.xdb` 生成工具；生成过程中会整理 IP 段，并对相邻区段、重复地域信息进行合并和压缩。[上游项目说明](https://github.com/lionsoul2014/ip2region)指出，原始数据会不定期更新。

![image-20261017122913384](https://pictured-bed.oss-cn-beijing.aliyuncs.com/img/2024/202610171229543.png)

两份 XDB 是从 [ip2region 官方 data 目录](https://github.com/lionsoul2014/ip2region/tree/master/data)同步的离线数据文件，不是 Java 依赖自动下载的数据，也不会在服务运行时联网更新。可使用 [`bin/local/update-ip2region.sh`](../../../../../../bin/local/update-ip2region.sh) 同步。旧的单文件 `ip2region.db`、`ip2region.xdb` 已从运行资源目录移除：它们不能替代双栈数据文件；`.db` 与 `.xdb` 是历史文件格式/代际差别，不代表 IPv4 与 IPv6。

`VisitorServiceImpl` 在创建 `visitor` 访客档案时写入 `visitor.ip_source`；`VisitLogServiceImpl` 在保存每次访问时也写入 `visit_log.ip_source`。当前新数据含五段，历史存量可为旧四段；城市聚合以第一段“中国”作为范围判断，并从第三段取城市名，兼容四段及以上格式。国家码字段当前仅随地域字符串保存，尚未用于全球聚合或地图关联。

**注意：** ip2region 负责“IP 解析为地域文本”，它不是城市经纬度坐标表；返回为空或城市字段缺失/为 `0` 时，该条地域不会进入当前城市 UV 聚合。缺失地域字段会保留分隔位置，例如 `Australia|Queensland|Brisbane||AU`，避免国家码错位。

**字典边界：** 当前后端没有单独维护“城市名 → 经纬度”的全球城市字典。后端的两份 XDB 职责是 IP → 国家/省/市/运营商/国家码文本；城市坐标映射在 CMS 前端的 `city2coord.json`，仍只覆盖中国城市，职责是城市名 → 经纬度。两份数据通过城市名称衔接。

#### 1.7.2 前端城市坐标字典：city2coord.json

前端字典位于 [`blog-cms-ui/src/util/city2coord.json`](../../../../../../blog-cms-ui/src/util/city2coord.json)，当前共 362 个城市映射项，来源注释指向 [Naccl/region2coord](https://github.com/Naccl/region2coord)。数据结构是“城市名 → [经度, 纬度]”，例如：

```json
{
  "北京市": ["116.4133836971231", "39.910924547299565"],
  "深圳市": ["114.06455183658751", "22.548456637984177"]
}
```

地域文本与坐标字典的连接键是城市名：`ip_source` 拆出的城市名写入 `city_visitor.city`，前端以这个名称查 `geoCoordMap[city]`。名称必须精确一致；缺少对应键时，前端不会猜坐标，而是跳过该城市点。因此该文件是中国城市坐标补充字典，不是与 ip2region 捆绑的后端资源。

#### 1.7.3 地图数据从后端到页面的流程

```text
IP 访问
  → Ip2Region 自动选择 ip2region_v4.xdb 或 ip2region_v6.xdb，解析为 ip_source
  → 从新访客的 ip_source 拆出城市名
  → 每日任务累加 city_visitor(city, uv)
  → GET /admin/dashboard 返回 cityVisitor（按 UV 降序）
  → city2coord.json 将城市名转为 [lng, lat]
  → ECharts map + geo + scatter + effectScatter 绘制
```

1. 组件在 `mounted()` 调用 `getData()`，通过 API 模块发起 `GET /admin/dashboard`。后端在一次响应中返回今日 PV/UV、历史 `visitRecord` 与城市 `cityVisitor`。
2. `cityVisitor` 的每项是 `{ city, uv }`，后端 SQL 已按 `uv desc` 排序。
3. `convertData()` 遍历城市列表，以 `city` 作为 key 查坐标，组装出 `{ name, value: [lng, lat], uv }`。坐标未匹配的项不加入图表数据，也不会显示错误地点。
4. 完整坐标数组设置到 `scatter` 系列；从数组前 5 项中拆出 Top 5 设置到 `effectScatter`。因为后端是 UV 降序，前 5 项就是 UV 最高的城市。
5. `mapOption` 里的 `geo.map="china"` 和 `map` 系列都使用已注册的中国地图。`geo` 是散点系列共用的地理坐标系；`map` 系列绘制中国底图，深色填充、蓝色省界线。地图中心设为 `[104.2, 36]`，`zoom=1.24`，`roam=false`，所以当前不能拖动或缩放底图。
6. 普通 `scatter` 点使用半径 5 的青色圆点，悬停 Tooltip 显示城市名和 UV；Top 5 `effectScatter` 点使用半径 12，增加波纹动效并直接显示城市名。
7. 窗口尺寸变化时对图表调用 `resize()`；离开组件时移除监听并 `dispose()` 释放图表实例。

**板块展示分工：** 中国省界和国家面是 ECharts 地图数据绘制的基底；城市经纬度点位由 `city2coord.json` 提供；`city_visitor.uv` 仅控制点位详情数值和城市 Top 5 排序，不用来调整普通点大小。

## 二、全球化 3D 访客地球调研与落地方案

### 2.1 目标、现状与总体落地顺序

本期在后台 `Dashboard` 下新增“全球访客地图”子栏目，并建立独立页面复刻[核心 MVP Demo](核心demo/全球3D访客地图核心Demo实现说明.md)的视觉和交互。现有数据概览页、二维中国访客地图、`/admin/dashboard` 接口及原有统计任务继续保留，二者并行运行。

建议路由结构如下：

```text
/dashboard
  /dashboard/overview             → 当前数据概览页（保留二维中国访客地图）
  /dashboard/global-visitor-map   → 新增全球访客地图页
```

**技术边界：** 已完成实测的 Demo 使用原生 Canvas 2D 球面投影产生 3D 地球观感，并非 Three.js、globe.gl 或 WebGL。它已经支持深色地球、自动旋转、拖拽、滚轮缩放、背面剔除、国家标签、城市悬停、中英文切换以及中国/国外热点榜单。因此正式工程优先复用这条 Canvas 路径，保证效果、性能和 Demo 一致。

当前可复用的地图能力包括：

| 能力 | 数据或实现来源 | 当前覆盖范围 |
| --- | --- | --- |
| 全球国家边界 | ECharts 4.9 `world.js` | 全球 ADM0 国家级边界 |
| 中国省级边界 | 独立 `china.js` 图层 | 中国省级行政区，与现有 Demo 展示一致 |
| 海外省州边界 | 精简后的本地 `adm1-mvp.js` | 10 个国家/地区、226 个 ADM1，约 312 KB；并非覆盖全球所有国家 |
| 访客热点 | 新接口返回的城市经纬度、UV、PV | 有真实统计数据的城市 |
| 无访客城市悬停 | 前端本地城市参考字典 | 用于地名浏览，不参与 UV/PV 统计 |
| 双语名称 | 接口城市中英文名 + 前端国家名称字典 | 同步切换地球标签、Tooltip 和榜单 |

城市定位是 IP 推断的近似地域，不是 GPS 精确位置；“放大看城市”表示展示城市点位、城市名和行政区边界，不包含道路、建筑或街道级地图。

本方案按依赖顺序落地：

```text
① 后端表结构与索引
  → ② 访问日志写入地域与 PV 标识
  → ③ 新增全球地图统一接口
  → ④ 前端新增独立页面并接入接口
  → ⑤ 经纬度投影、热点、榜单和双语渲染
  → ⑥ 历史回填、性能优化与验收
```

**重点：** 正式页面从第一版就调用新接口。首期接口可以返回后端 classpath 中的模拟数据；切换真实查询时只替换后端数据提供者，接口地址、响应结构和前端渲染逻辑不变。

### 2.2 后端落地：先改表与写入链路，再提供统一接口

后端工作按“确认事实源 → 补最小字段 → 写入标准地域 → 查询聚合 → 对外接口”的顺序实施。

**第一步：确认现有表的职责与缺口。**

| 表 | 可复用能力 | 处理结论 |
| --- | --- | --- |
| `visit_log` | 保存 UUID、IP、`ip_source`、行为和发生时间，是每次访问事件的事实源 | 作为全球 PV/UV 的事实表，补充 PV 标识、地域关联、解析状态和查询索引 |
| `visitor` | 保存访客首次/当前状态及累计 PV | 无法还原周期内跨城市访问，不作为全球地图事实源，不扩字段 |
| `city_visitor` | 保存中国城市历史累计新增 UV | 继续服务旧二维地图，不改造成全球表 |
| `visit_record` | 保存全站每日 PV/UV 趋势 | 没有地域维度，继续服务旧趋势图 |

全球接口必须回到 `visit_log` 计算：PV 是统计周期内符合页面浏览口径的访问事件数；UV 是对应层级内按 UUID 去重的访客数。全球 UV、国家 UV、城市 UV 必须分别去重，不能把城市 UV 或国家 UV 直接相加得到全球 UV。

**第二步：使用一张精简地域维表，并仅给访问日志增加三个字段。**

```sql
CREATE TABLE `visitor_geo` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `geo_key` varchar(160) NOT NULL COMMENT '稳定地域键，例如 CN|GD|SHENZHEN',
  `geo_level` tinyint NOT NULL COMMENT '1国家，2城市',
  `country_code` char(2) NOT NULL COMMENT 'ISO 3166-1 Alpha-2',
  `region_name` varchar(128) DEFAULT NULL COMMENT '匹配区域名并区分同名城市',
  `city_name_zh` varchar(128) DEFAULT NULL,
  `city_name_en` varchar(128) DEFAULT NULL,
  `longitude` decimal(10,6) DEFAULT NULL,
  `latitude` decimal(9,6) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_visitor_geo_key` (`geo_key`),
  KEY `idx_visitor_geo_country_level` (`country_code`, `geo_level`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

ALTER TABLE `visit_log`
  ADD COLUMN `is_page_view` bit(1) DEFAULT NULL COMMENT '是否计入页面 PV',
  ADD COLUMN `geo_id` bigint DEFAULT NULL COMMENT '关联 visitor_geo.id',
  ADD COLUMN `geo_status` tinyint NOT NULL DEFAULT 0 COMMENT '0未知，1已定位，2内网IP，3无效IP',
  ADD KEY `idx_visit_map_query` (`is_page_view`, `create_time`, `geo_id`, `uuid`);
```

该结构已去除当前接口和渲染不需要的字段：不重复保存 `event_type`、IP 版本、国家中英文名、城市编码、定位精度、单行数据来源/版本、启停状态和行级时间戳。国家名称由前端 ISO 字典转换；国家多边形、标签中心和 ADM1 图形属于前端地图资源；地域字典的数据来源和版本统一记录在 README 或更新清单中。

`visit_log.geo_id` 首期不强制建立数据库外键，避免高频写入和历史回填受外键锁及写入顺序影响。`ip_source` 继续保留为原始解析快照和排查依据，但不再作为统计分组键。`visitor_geo` 通过离线字典初始化并在服务中只读缓存，不应在每次访问时临时插入；城市无法可靠命中时降级到国家级。

**第三步：改造访问日志写入链路。**

```text
@VisitLogger 捕获访问事件
  → 根据 VisitBehavior 的“是否计入 PV”属性写入 is_page_view
  → IpAddressUtils 解析国家、区域、城市、运营商、国家码
  → 地域标准化服务匹配 visitor_geo
      ├─ 城市命中：geo_status=1，写城市 geo_id
      ├─ 仅国家命中：geo_status=1，写国家 geo_id
      └─ 未知/内网/无效：写 0/2/3，geo_id 为空
  → 异步写入 visit_log
```

`VisitBehavior` 增加布尔型“是否计入 PV”属性即可，不再通过中文行为文本判断，也无需在数据库重复存储事件类型。首页、归档、动态、友链、关于、博客详情、分类、标签和搜索可按产品口径计入页面访问；点赞、点击友链、密码校验等交互默认不计入 PV，最终名单通过枚举及单元测试固化。

**第四步：新增全球地图专用接口。**

```http
GET /admin/visitor-map/global?periodType=rolling_24h&timezone=Asia%2FShanghai
```

接口独立于 `/admin/dashboard`，避免全球地图的数据体积、缓存和统计周期拖慢原概览页。首期 `periodType` 默认且只需支持 `rolling_24h`，`timezone` 默认 `Asia/Shanghai`；后续可增加自然日、周、月等明确枚举。

建议后端模块结构：

```text
GlobalVisitorMapAdminController
  → GlobalVisitorMapService
      → MockGlobalVisitorMapProvider       # 首期读取 classpath JSON
      → DatabaseGlobalVisitorMapProvider   # 后续查询 visit_log + visitor_geo
  → GlobalVisitorMapVO                     # 两种 Provider 共用同一契约
```

首期将 Demo 的 `data.json` 同步为
`blog-backend/src/main/resources/visitor-map/global-visitor-map.mock.json`。Controller 负责参数校验和统一 `Result` 返回；Service 选择 Provider；不要直接返回任意 `Map<String, Object>`，应为元信息、汇总、国家项和城市项建立明确 VO。

建议响应结构：

```json
{
  "code": 200,
  "msg": "获取成功",
  "data": {
    "meta": {
      "schemaVersion": "1.0",
      "dataMode": "mock",
      "generatedAt": "2026-10-17T10:40:00+08:00",
      "periodType": "rolling_24h",
      "periodStart": "2026-10-16T10:40:00+08:00",
      "periodEnd": "2026-10-17T10:40:00+08:00",
      "timezone": "Asia/Shanghai",
      "coordinateSystem": "WGS84",
      "quality": {
        "resolvedPv": 15820,
        "countryOnlyPv": 210,
        "unknownPv": 158
      }
    },
    "summary": {
      "uv": 6789,
      "pv": 16188,
      "countryCount": 19,
      "cityCount": 40
    },
    "countries": [
      {"countryCode": "CN", "uv": 3927, "pv": 9450}
    ],
    "cities": [
      {
        "geoKey": "CN|BJ|BEIJING",
        "cityNameZh": "北京市",
        "cityNameEn": "Beijing",
        "countryCode": "CN",
        "lat": 39.910925,
        "lng": 116.413384,
        "uv": 520,
        "pv": 1280
      }

  }

```

接口必须返回该周期内全部可展示城市，Top 20 只是前端榜单规则，不能用 `topN` 截断 `cities[]`，否则榜外城市会从地球热点中消失。由于城市只覆盖精确命中的事件，允许“城市 PV 合计 < 国家 PV 合计 < 全球 PV”；差额由 `meta.quality` 解释，不能把未知访问强行归入城市。接口不得返回原始 IP 或 UUID。

真实 Provider 第一版直接查询 `visit_log + visitor_geo`：

- 全球 PV：周期内 `is_page_view=1` 的日志数；
- 全球 UV：周期内 `COUNT(DISTINCT uuid)`；
- 国家 PV/UV：按 `country_code` 分组分别统计；
- 城市 PV/UV：仅对城市级 `geo_id` 分组分别统计；
- 数据质量：按 `geo_status` 统计已定位、内网、无效和未知事件；
- 国家数、城市数：统计周期内有访问数据的去重地域数。

首期不新增聚合表。只有事实表查询出现明确性能瓶颈后，再评估 `visitor_map_agg`、缓存、Bitmap 或 HyperLogLog。尤其不能把小时 UV 相加成滚动 24 小时 UV，同一访客跨小时会被重复计算。

历史数据采用“新字段允许为空 → 新写入先上线 → 按主键或时间分批回填”的方式处理。`is_page_view` 依据历史 URI、行为和枚举映射回填；地域优先解析现有 `ip_source`，必要且符合数据保留策略时再使用 IP 查询当前 XDB。任务需记录所用 XDB 版本及成功、国家级、未匹配、内网、失败数量，并支持断点续跑。

### 2.3 前端落地：新增独立页面并完成地图数据渲染

前端工作按“菜单与页面 → 本地地图资源 → 接口数据适配 → Canvas 渲染 → 交互与性能”的顺序实施。当前技术栈为 Vue 2.6、Vue Router 3、Element UI 2、ECharts 4.9 和原生 Canvas。

**第一步：新增 Dashboard 子路由和页面组件。**

将 Dashboard 调整为带 `Layout` 的父级菜单并设置 `alwaysShow: true`；`/dashboard` 重定向到 `/dashboard/overview`，保证旧入口仍落到原数据概览页。建议文件组织：

```text
blog-cms-ui/src/views/dashboard/
  index.vue                         # 原数据概览页，不删除原二维地图
  global-visitor-map/index.vue      # 新页面：请求、状态、布局和交互编排
blog-cms-ui/src/components/VisitorGlobe/
  GlobeCanvas.vue                   # Canvas 尺寸、生命周期和事件桥接
  renderer.js                       # 投影、绘制、命中、动画
blog-cms-ui/src/api/visitor-map.js  # 全球访客地图接口
```

Demo 不能通过 iframe 嵌入后台，也不能继续引用文档目录中的相对 `node_modules`。正式组件使用 CMS 已有 npm 依赖打包，`world.js`、`china.js`、精简 ADM1 和城市参考字典均作为本地资源，不使用 CDN。

**第二步：明确经纬度和地图资源的职责。**

- 后端 `cities[].lat/lng` 是访客城市的 WGS84 代表坐标，用于绘制发光点、命中区域和 Tooltip；
- 后端 `countries[].countryCode` 用于关联国家多边形并计算国家热度；
- 前端 ADM0/ADM1 文件只负责国家、省州边界，不承载访客统计；
- 前端城市参考字典负责“没有访客也能悬停查看城市名”，不计入 PV/UV；
- 前端国家 ISO 字典负责国家中英文名称，后端不重复存储；
- 中国省界继续使用独立 `china.js` 图层，保证与 Demo 及原有中国版图表现一致。

**第三步：按统一数据流完成渲染。**

```text
GET /admin/visitor-map/global
  → 校验 Result.data 并补默认空数组
  → meta/summary 渲染周期、PV、UV、国家数、城市数
  → countries[] 按 countryCode 建索引，映射国家填充强度
  → cities[] 读取 lat/lng，投影为球面坐标并绘制热点
  → 本地城市参考字典补充无访客城市悬停
  → 按 countryCode === 'CN' 拆分中国/国外榜单
  → 两组分别按 UV 降序取 Top 20，并独立滚动
```

语言状态由页面统一管理。切换中英文时，国家标签、城市标签、ADM1 名称、Tooltip、榜单和辅助文案同步刷新；Canvas renderer 只接收标准数据、当前语言与视角状态，不负责发请求。接口加载失败时展示明确错误态和重试按钮，不能静默回退到前端陈旧数据。

**第四步：保留 Demo 交互并落实性能约束。**

页面应支持自动旋转、拖拽旋转、滚轮缩放、城市/行政区悬停、国家标签常驻、暂停或放大后展示更多 ADM1/城市名称，以及中国/国外 Top 20 榜单。为保证流畅度：

- 新页面使用路由懒加载；
- 组件挂载且页面可见时才启动 `requestAnimationFrame`；
- 页面隐藏、组件销毁时停止动画并清理 Pointer、Wheel、Resize 监听；
- 限制设备像素比，避免高分屏把 Canvas 像素量无限放大；
- 旋转期间减少 ADM1、文字和命中检测，暂停或放大后再绘制细节；
- 静态边界预处理并缓存投影前数据，统计更新时只更新热度和热点；
- 不在每一帧重新排序榜单或创建大量临时对象。

前端最终只依赖接口契约，不关心数据是 mock 还是真实查询。这样首期可先验收页面效果，后端切换 `DatabaseGlobalVisitorMapProvider` 时无需再次改造渲染代码。

### 2.4 分阶段实施与验收

| 顺序 | 实施内容 | 主要产物 | 验收标准 |
| --- | --- | --- | --- |
| 1. 数据模型 | 新增 `visitor_geo`；扩展 `visit_log` 三个字段和组合索引 | 增量 SQL、地域初始化数据 | 国内外城市具备国家码、中英文名和 WGS84 经纬度；旧表和旧地图不受影响 |

| 3. 新接口 | 新增 Controller、VO、Service 和两种 Provider；首期启用 mock | `GET /admin/visitor-map/global` | 参数、周期、质量指标、空数据和错误返回稳定；不暴露 IP/UUID |

| 5. 数据渲染 | 接入接口，渲染国家、城市热点、无访客城市、双语和两组 Top 20 | 页面完整交互 | 旋转、缩放、悬停、榜单、语言同步及错误重试与 Demo 一致 |
| 6. 真实数据 | 启用 Database Provider，按需回填历史日志 | Mapper、回填任务、质量报表 | 各层级 PV/UV 可复算，未知数据可解释，前端无需改代码 |
| 7. 性能优化 | 仅在监控确认瓶颈后增加缓存或聚合结构 | 压测报告、可选聚合方案 | 查询耗时与动画帧率达到上线目标，UV 口径不因预聚合失真 |

首个可演示里程碑可以在第 3～5 步完成：后端统一接口暂时返回模拟数据，前端已使用正式路由、正式接口和本地地图资源展示完整效果。正式统计上线则必须完成第 1、2、3、6 步，不能把 ip2region 已支持全球 IP 解析等同于全球 PV/UV 已经具备。

**最终验收重点：**

1. 旧 Dashboard、旧二维中国地图、`city_visitor` 和 `/admin/dashboard` 均保持可用；
2. 新页面只通过 `/admin/visitor-map/global` 获取统计数据；
3. 国家、城市和经纬度职责清晰，榜单 Top 20 不截断地球热点；
4. 中文/英文切换同步作用于地球内部标签、Tooltip 和榜单；
5. 中国版图保持 Demo 已验证的独立图层效果，海外 ADM1 明确展示当前覆盖范围；
6. 全球、国家、城市 PV/UV 分层计算，未定位数据通过质量字段可解释；
7. Demo 保留为视觉与契约基准，但不成为生产页面的运行依赖。

## 三、ip2region 双栈数据与本地验证改造

### 3.1 本次优化改造内容

访客地图要迈向全球化，首先需要保证服务端能够稳定识别 IPv4、IPv6，并且地域字段调整后仍能正确进入现有中国城市 UV 聚合。本次改造先完成 IP 地域查询基础设施的双栈化；这不等于全球地图统计和全球城市聚合已经完成。

1. **数据文件改为官方双栈 XDB。** 后端资源目录现在使用 `ip2region_v4.xdb` 和 `ip2region_v6.xdb`，分别供 IPv4、IPv6 查询。历史单文件 `ip2region.db`、`ip2region.xdb` 已移出运行资源目录；`.db` 与 `.xdb` 是历史格式/代际差异，不代表 IPv4 与 IPv6。数据从 [ip2region 官方仓库](https://github.com/lionsoul2014/ip2region) 的 [data 目录](https://github.com/lionsoul2014/ip2region/tree/master/data)获取。

2. **升级查询依赖并统一服务生命周期。** `org.lionsoul:ip2region` 从 `2.6.5` 升级到 `3.3.7`。原先依赖静态 `Searcher` 和反射调用的单文件查询方式，改为 Spring 管理的 `IpAddressUtils` 服务：启动时从 classpath 流分别加载 v4/v6 数据，以 `BufferCache` 缓存在内存中，由同一个 `Ip2Region` 实例自动按 IP 版本路由；应用关闭时释放查询服务。该加载方式也适用于 Spring Boot 可执行 JAR 内的资源。

3. **统一地域字段并兼容旧数据形态。** 查询结果按 `Country|Province|City|ISP|ISO-Alpha2` 五段处理；缺失值及上游的 `0` 会规范为空字符串，同时保留字段位置，例如 `Australia|Queensland|Brisbane||AU`，避免空 ISP 导致国家码错位。`VisitLogServiceImpl` 与 `VisitorServiceImpl` 改为注入统一查询服务，新增访问日志和访客记录共用相同的地域解析逻辑。

4. **保护现有中国城市 UV 汇总。** `VisitorSyncScheduleTask` 改为保留空字段拆分，兼容旧四段及新五段格式；仍仅汇总国家字段为“中国”、且城市字段有效的新增访客 UV，并跳过空值或 `0` 城市。**注意：** 当前这一步只保证 IPv4/IPv6 都可解析，并让已有中国聚合兼容新格式；全球国家/城市的 PV、UV 聚合和全球统计表仍需后续设计实现。

5. **增加可重复的数据更新流程。** 在仓库根目录运行 [`./bin/local/update-ip2region.sh`](../../../../../../bin/local/update-ip2region.sh)，脚本从官方 data 地址下载 v4、v6 两个文件，先暂存并做基本大小校验，两个文件都下载成功后才替换目标文件，并输出 SHA-256。网络环境需要镜像时可通过 `IP2REGION_BASE_URL` 覆盖下载根地址。资源目录中的 [`ipdb/README.md`](../../../../../../blog-backend/src/main/resources/ipdb/README.md) 与 [`bin/local/README.md`](../../../../../../bin/local/README.md) 记录了来源和操作方式。两份数据库合计约 47 MB，会随后端资源打包，并在服务启动时加载到内存。

#### 验证方式与边界

- **离线单元测试：** [`IpAddressUtilsTest`](../../../../../../blog-backend/src/test/java/com/changlu/blogloom/util/IpAddressUtilsTest.java) 使用本地 XDB 分别验证 IPv4 海外样例 `1.2.3.4`（澳大利亚布里斯班）和 IPv6 中国样例（深圳），检查统一查询服务的解析结果及五段字段格式。可在 `blog-backend` 目录执行 `mvn -Dtest=IpAddressUtilsTest test`；该测试不访问公网。本次本地执行结果为 1 项通过、0 失败。
- **当前机器手动检查：** [`IpAddressCurrentMachineCheck`](../../../../../../blog-backend/src/test/java/com/changlu/blogloom/util/IpAddressCurrentMachineCheck.java) 先尝试用 `curl` 访问 `https://api.ipify.org` 获取公网出口 IP，再用本地 XDB 查询并打印 IP 和地域；外网服务不可达时会回退到本机活动网卡地址。该类名不以 `Test` 结尾，不属于 Maven 默认全量测试；可在 IDE 中手动运行其 JUnit 方法。公网 IP 服务访问失败（例如 curl exit code 7、TLS 握手失败）代表当前网络无法连接外部 IP 查询站点，不等同于本地 ip2region 数据库查询失败。回退得到的内网 IP 通常无法反映机器的公网地理位置。

**结论：** 本次改造完成了 IP 地域库的 IPv4/IPv6 双栈接入、地域字段兼容、离线验证和数据更新入口，为全球访客地图提供底层能力；全球 PV/UV 口径、全球聚合存储及地图接口仍属于后续工作，不应将本次双栈解析能力误认为全球统计已落地。
